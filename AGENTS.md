# AGENTS.md

Guidance for AI coding agents (Cursor and others) working on NPO.WorkDash. Humans are welcome too: this is the short version of how work gets done here. The [README](README.md) has the full local setup.

## Project

Hosted multi-tenant SaaS for UK charities and CICs. APES is tenant #1.

- **Stack**: Laravel 12 (PHP 8.3), React 19 with Inertia and TypeScript, Tailwind 4, Vite 7, MySQL 8.0, Pest 4. Decisions are in [docs/adr](docs/adr/README.md).
- **Backend**: `app/`, `routes/`, `database/` (migrations, factories, seeders), `config/`.
- **Frontend**: `resources/js/` (`pages/`, `components/`, `layouts/`, `hooks/`, `lib/`, `types/`). `resources/js/routes`, `actions` and `wayfinder` are generated by Wayfinder and gitignored.
- **Tests**: `tests/Feature`, `tests/Unit` (Pest).
- **Deploy**: `deploy/cloudron/` and [docs/deploy/cloudron.md](docs/deploy/cloudron.md).
- **Repository**: `APESCIC/NPO.WorkDash`, default branch `main`.

## Non-negotiables

- **Tenant isolation** ([ADR 0002](docs/adr/0002-tenancy.md)): every tenant-owned table has an indexed `tenant_id`, every tenant-owned model uses the tenant scope, and every such model gets an isolation test. A missed scope is a data breach.
- **Clean room** ([ADR 0005](docs/adr/0005-clean-room.md)): never copy WorkDo (or other proprietary) code, schemas, templates or assets. Third-party code only arrives through Composer or npm under a SaaS-compatible licence.
- **No real personal data** in seeders, tests or fixtures. Use the `example.test` domain; a test enforces this.
- **Secrets** never go into git, issues, PRs or chat. See [docs/security/secrets.md](docs/security/secrets.md). gitleaks runs in CI.
- MySQL 8.0 in production: avoid 8.4-only SQL.

## Local preview

Check for a running server before starting one.

- **Laragon (preferred)**: Laragon running, then `npm run dev`. Open <http://npo-workdash.test>. Mail goes to Mailpit at <http://127.0.0.1:8025>.
- **Without Apache**: `composer dev` serves <http://127.0.0.1:8000> with the queue worker and Vite (set `APP_URL` to match).
- Reset data: `php artisan migrate:fresh --seed` (demo login `demo@example.test` / `password`).

## Checks

Run these before pushing. CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs the same and must be green before merge.

```powershell
composer test            # Pint style check, then Pest
composer analyse         # Larastan level 5
npm run lint:check       # ESLint
npm run format:check     # Prettier
npm run types:check      # tsc
composer ci:check        # all of the above except the Vite build
```

Fix style with `composer lint` (Pint) and `npm run lint` / `npm run format`.

## Code conventions

- Match the surrounding code. Laravel Pint `laravel` preset; Prettier with the Tailwind plugin.
- Imports at the top of the file, no inline imports.
- In TypeScript `switch` statements over unions or enums, end with a `default` that assigns to `never`, so new variants fail to compile.
- Comments only for constraints the code cannot show.
- Every behaviour change ships with Pest tests (feature tests for HTTP and jobs, isolation tests for tenant models).
- Migrations are expand-first (add, backfill, then remove in a later release) so `rollback.sh` stays safe.

## Work lifecycle

Every change-making task follows this, start to finish. Use `gh`; GitHub MCP is optional.

### 1. Issue and milestone

1. Search first: `gh issue list --search "<keywords>" --state open`. Reuse a fitting issue; create one only if none fits.
2. Title prefix and label by type: `[Epic]` (multi-PR initiative), `[Story]` (user-facing slice), `[Task]`, `[Bug]`, `[Chore]`. Add the area labels used on sibling issues (for example `foundation`, `devops`, `p1-mvp`).
3. Body sections, as on existing issues: Summary, Context / why, Scope, Acceptance criteria (checkboxes), Out of scope, Dependencies.
4. Set the milestone (`M0 Foundation` to `M8 Launch`, `M0.5 Install and updates`): `gh issue edit <n> --milestone "<title>"`.
5. Link it under its parent story or epic:

   ```powershell
   $id = gh api repos/APESCIC/NPO.WorkDash/issues/<child> --jq '.id'
   gh api -X POST repos/APESCIC/NPO.WorkDash/issues/<parent>/sub_issues -F sub_issue_id=$id
   ```

6. If the work splits, open sub-issues and link them the same way.

### 2. Branch

Never commit to `main`. Branch from an up-to-date `main`:

- `cursor/feature/<issue>-<slug>`, `cursor/fix/<issue>-<slug>` or `cursor/chore/<issue>-<slug>` (lowercase kebab-case slug).
- Reuse the branch if one already exists for the issue. Push with `git push -u origin <branch>`; never force-push.

### 3. While working

Comment on the issue when something load-bearing happens: a decision, a blocker, a scope change, or the PR opening (`gh issue comment <n> --body "..."`). Tick acceptance criteria as they are met.

### 4. Definition of done

Work is not done until it is **committed, merged, released and deployed**:

1. **Commit** focused commits with imperative messages.
2. **Release notes in the PR**: add the change under `## [Unreleased]` in [CHANGELOG.md](CHANGELOG.md), then move it into a new `## [X.Y.Z] - YYYY-MM-DD` section and set [VERSION](VERSION) to `X.Y.Z`. While the major version is 0: **minor** for features or breaking changes, **patch** for fixes, chores and docs. Update the compare links at the bottom.
3. **PR**: `gh pr create --base main --milestone "<milestone>"` using the [PR template](.github/pull_request_template.md), with `Closes #<issue>`.
4. **CI green**: `gh pr checks <pr> --watch`. Fix failures; do not merge red.
5. **Merge**: `gh pr merge <pr> --squash --delete-branch`, then `git checkout main; git pull --ff-only`.
6. **Release**: tag the merge commit and publish the changelog section:

   ```powershell
   git tag -a vX.Y.Z -m "vX.Y.Z" <merge-sha>; git push origin vX.Y.Z
   gh release create vX.Y.Z --title "vX.Y.Z" --notes "<the CHANGELOG section>"
   ```

7. **Deploy** to Cloudron (below) and verify.
8. **Close out**: confirm the issue closed (or close it with a comment linking the PR and release), close parents only when all children are done, and check the milestone's progress.

If several PRs are in flight, the one merged second rebases and takes the next version.

## Deploying to Cloudron

| | |
| --- | --- |
| Production URL | <https://npo-workdash.apes.org.uk/> |
| Cloudron app ID | `b253bb6f-f66a-49cc-aa7f-79464eebdc91` (LAMP app) |
| Staging | none yet |

The `cloudron` CLI must be logged in (`cloudron list` works). Deploy a tag from Git Bash, or from PowerShell through Git Bash:

```powershell
& "C:\Program Files\Git\bin\bash.exe" deploy/cloudron/cloudron-deploy.sh vX.Y.Z
```

The script builds the release, pushes it, runs `deploy.sh` on the app, restarts it, and fails unless `/up` returns 200 and the live `REVISION` matches the tag. `--bootstrap` is only for a fresh app. Full details, rollback and troubleshooting: [docs/deploy/cloudron.md](docs/deploy/cloudron.md).

Cloudron caveats:

- On the app, always use `php8.3` and `gosu www-data php8.3 /app/data/workdash/artisan ...`; plain `php` is the image default and `su` drops the Cloudron environment.
- The LAMP `start.sh` **sources** `/app/data/run.sh` under `set -eu`. Keep all code inside its `( ... )` subshell, or the app crash-loops before Apache starts (recovery: `cloudron debug`, see the guide's Troubleshooting).
- From PowerShell, quote the separator: `cloudron exec --app <id> '--' ls /app/data`. From Git Bash, prefix `cloudron` calls that take remote paths with `MSYS_NO_PATHCONV=1`.
- Rolling back code does not roll back migrations.
- Other agent sessions may be working in parallel (`git worktree list`, `gh pr list`). Check before deploying, and do not deploy a tag that would undo a fix still waiting to merge.

## Decisions and next steps

Whenever a choice is needed (or at the end of a task), give the **best next options** and mark **one as recommended**, with a one-line reason each. In Cursor, ask with the AskQuestion tool, recommended option first and labelled "(Recommended)". Do not stop with a vague "done": end with what shipped (PR, merge commit, release, deploy evidence) and the next options.
