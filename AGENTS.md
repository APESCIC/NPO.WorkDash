# AGENTS.md

Guidance for AI coding agents (Cursor and others) working on NPO.WorkDash. Humans are welcome too: this is the short version of how work gets done here. The [README](README.md) has the full local setup.

## Project

Hosted multi-tenant SaaS for UK charities and CICs. APES is tenant #1.

- **Stack**: Laravel 12 (PHP 8.3), React 19 with Inertia and TypeScript, Tailwind 4, Vite 7, MySQL 8.0, Pest 4. Decisions are in [docs/adr](docs/adr/README.md).
- **Backend**: `app/`, `routes/`, `database/` (migrations, factories, seeders), `config/`.
- **Frontend**: `resources/js/` (`pages/`, `components/`, `layouts/`, `hooks/`, `lib/`, `types/`). `resources/js/routes`, `actions` and `wayfinder` are generated by Wayfinder and gitignored.
- **Tests**: `tests/Feature`, `tests/Unit` (Pest).
- **Deploy**: `deploy/cloudron/` and [docs/deploy/cloudron.md](docs/deploy/cloudron.md).
- **Repository**: `APESCIC/NPO.WorkDash`, default branch `main`, on two hosts (below).

## Where things live

| | [Gitea](https://gitea.intranet.apes.org.uk/APESCIC/NPO.WorkDash) (primary, `origin`) | [GitHub](https://github.com/APESCIC/NPO.WorkDash) (`github` remote) |
| --- | --- | --- |
| Code | Every branch, `main` and tags | Branches pushed for CI, then `main` and tags after each merge |
| Issues and milestones | Yes | Turned off |
| Pull requests, review, merge | Yes | Draft "CI only" PRs, never merged |
| CI, releases, update feeds | No Actions runner | GitHub Actions, GitHub Releases, GitHub Pages (`gh-pages`) |

Use `tea` for Gitea and `gh` for GitHub. One-time setup in a fresh clone:

```powershell
git remote add github https://github.com/APESCIC/NPO.WorkDash.git
tea login list   # an `apes` login for https://gitea.intranet.apes.org.uk
gh auth status
```

Run `tea` inside the clone so `{owner}` and `{repo}` resolve from `origin`. Do not add a Gitea push mirror to GitHub: it force-pushes every ref and would overwrite `gh-pages`, which serves the update feeds.

## Non-negotiables

- **Tenant isolation** ([ADR 0002](docs/adr/0002-tenancy.md)): every tenant-owned table has an indexed `tenant_id`, every tenant-owned model uses the tenant scope, and every such model gets an isolation test. A missed scope is a data breach.
- **Clean room** ([ADR 0005](docs/adr/0005-clean-room.md)): never copy WorkDo (or other proprietary) code, schemas, templates or assets. Third-party code only arrives through Composer or npm under a SaaS-compatible licence.
- **No real personal data** in seeders, tests or fixtures. Use the `example.test` domain; a test enforces this.
- **Secrets** never go into git, issues, PRs or chat. See [docs/security/secrets.md](docs/security/secrets.md). gitleaks runs in CI.
- MySQL 8.0 in production: avoid 8.4-only SQL.

## Local preview

Check for a running server before starting one.

- **Laragon (preferred)**: Laragon running, then `npm run dev`. Open <http://npo-workdash.test>. Mail goes to Mailpit at <http://127.0.0.1:8025>.
- **Without Apache**: `composer dev` serves <http://127.0.0.1:8000> with the queue worker and Vite (set `APP_URL` to match).
- Reset data: `php artisan migrate:fresh --seed` (demo login `demo@example.test` / `password`).

## Checks

Run these before pushing. CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs the same on GitHub, through the draft CI PR in step 4 of the definition of done, and must be green before merge.

```powershell
composer test            # Pint style check, then Pest
composer analyse         # Larastan level 5
npm run lint:check       # ESLint
npm run format:check     # Prettier
npm run types:check      # tsc
composer ci:check        # all of the above except the Vite build
```

Fix style with `composer lint` (Pint) and `npm run lint` / `npm run format`.

## Code conventions

- Match the surrounding code. Laravel Pint `laravel` preset; Prettier with the Tailwind plugin.
- Imports at the top of the file, no inline imports.
- In TypeScript `switch` statements over unions or enums, end with a `default` that assigns to `never`, so new variants fail to compile.
- Comments only for constraints the code cannot show.
- Every behaviour change ships with Pest tests (feature tests for HTTP and jobs, isolation tests for tenant models).
- Migrations are expand-first (add, backfill, then remove in a later release) so `rollback.sh` stays safe.

## Work lifecycle

Every change-making task follows this, start to finish. Issues and PRs live on Gitea (`tea`); CI and releases run on GitHub (`gh`).

### 1. Issue and milestone

1. Search first: `tea issues ls --keyword "<keywords>" --state open`. Reuse a fitting issue; create one only if none fits.
2. Title prefix and label by type: `[Epic]` (multi-PR initiative), `[Story]` (user-facing slice), `[Task]`, `[Bug]`, `[Chore]`. Add the area labels used on sibling issues (for example `foundation`, `devops`, `p1-mvp`); `tea labels ls` lists them.
3. Body sections, as on existing issues: Summary, Context / why, Scope, Acceptance criteria (checkboxes), Out of scope, Dependencies (`Parent epic: #<n>` or `Parent story: #<n>`, then anything it depends on).
4. Milestones are named after the release that ships them, `v0.3.0 SaaS core` to `v1.0.0 Launch` (`tea milestones ls`). Create the issue with its labels and milestone in one go, writing the body to a file first:

   ```powershell
   tea issues create --title "[Chore] ..." --description-file <body.md> --labels "chore,devops" --milestone "v0.3.0 SaaS core"
   ```

   Change the milestone later with `tea issues edit <n> --milestone "<title>"`.
5. Link it under its parent story or epic. Gitea has no sub-issues, so make the parent depend on the child; Gitea then refuses to close the parent while the child is open:

   ```powershell
   tea api -X POST "/repos/{owner}/{repo}/issues/<parent>/dependencies" -f owner=APESCIC -f repo=NPO.WorkDash -F index=<child>
   ```

   `tea api "/repos/{owner}/{repo}/issues/<parent>/dependencies"` lists the children.
6. If the work splits, open more issues and link them the same way.

### 2. Branch

Never commit to `main`. Branch from an up-to-date `main`:

- `cursor/feature/<issue>-<slug>`, `cursor/fix/<issue>-<slug>` or `cursor/chore/<issue>-<slug>` (lowercase kebab-case slug).
- Reuse the branch if one already exists for the issue. Push with `git push -u origin <branch>`, and to `github` when CI should run (step 4 below); never force-push.

### 3. While working

Comment on the issue when something load-bearing happens: a decision, a blocker, a scope change, or the PR opening (`tea comment <n> "..."`). Tick acceptance criteria as they are met (`tea issues edit <n> --description-file <body.md>`).

### 4. Definition of done

Work is not done until it is **committed, merged, released and deployed**:

1. **Commit** focused commits with imperative messages.
2. **Release notes in the PR**: add the change under `## [Unreleased]` in [CHANGELOG.md](CHANGELOG.md), then move it into a new `## [X.Y.Z] - YYYY-MM-DD` section and set [VERSION](VERSION) to `X.Y.Z`. While the major version is 0: **minor** for features or breaking changes, **patch** for fixes, chores and docs. Update the compare links at the bottom.
3. **PR on Gitea** using the [PR template](.github/pull_request_template.md), with `Closes #<issue>`:

   ```powershell
   tea pulls create --base main --head <branch> --title "..." --description-file <pr.md> --milestone "<milestone>" --labels "<labels>"
   ```

4. **CI green on GitHub**: GitHub only runs workflows for its own PRs and pushes, so open a draft PR there that runs the checks and is never merged. Push every later commit to both remotes; the draft PR picks it up.

   ```powershell
   git push github <branch>
   gh pr create -R APESCIC/NPO.WorkDash --draft --base main --head <branch> --title "CI only: <title>" --body "Checks for <Gitea PR URL>. Review and merge happen on Gitea."
   gh pr checks <github-pr> -R APESCIC/NPO.WorkDash --watch
   ```

   Link the green checks in a comment on the Gitea PR. Fix failures; do not merge red.
5. **Merge on Gitea, then bring GitHub up to date**:

   ```powershell
   tea pulls merge <pr> --style squash
   git push origin --delete <branch>
   git checkout main; git pull --ff-only
   git push github main
   gh pr close <github-pr> -R APESCIC/NPO.WorkDash --delete-branch --comment "Merged on Gitea: <Gitea PR URL>"
   ```

6. **Release**: tag the merge commit and push the tag to both hosts. The [Release workflow](.github/workflows/release.yml) runs on GitHub: it builds the signed zip, creates the GitHub release with the CHANGELOG section as notes (a pre-release for `-beta.N` tags) and refreshes the update feeds. The GitHub release is the one installs download from; Gitea only gets the tag. Wait for it to pass:

   ```powershell
   git tag -a vX.Y.Z -m "vX.Y.Z" <merge-sha>; git push origin vX.Y.Z; git push github vX.Y.Z
   gh run watch -R APESCIC/NPO.WorkDash (gh run list -R APESCIC/NPO.WorkDash --workflow release.yml --limit 1 --json databaseId --jq '.[0].databaseId') --exit-status
   ```

   Details and signing-key handling: [docs/security/release-signing.md](docs/security/release-signing.md).

7. **Deploy** to Cloudron (below) and verify.
8. **Close out**: confirm the issue closed (or close it with `tea comment <n> "..."` linking the PR and release, then `tea issues close <n>`), close parents only when all children are done, and check the milestone's progress (`tea milestones ls`).

If several PRs are in flight, the one merged second rebases and takes the next version.

## Deploying to Cloudron

| | |
| --- | --- |
| Production URL | <https://npo-workdash.apes.org.uk/> |
| Cloudron app ID | `b253bb6f-f66a-49cc-aa7f-79464eebdc91` (LAMP app) |
| Staging | none yet |

The `cloudron` CLI must be logged in (`cloudron list` works). Deploy a tag from Git Bash, or from PowerShell through Git Bash:

```powershell
& "C:\Program Files\Git\bin\bash.exe" deploy/cloudron/cloudron-deploy.sh vX.Y.Z
```

The script builds the release, pushes it, runs `deploy.sh` on the app, restarts it, and fails unless `/up` returns 200 and the live `REVISION` matches the tag. `--bootstrap` is only for a fresh app. Full details, rollback and troubleshooting: [docs/deploy/cloudron.md](docs/deploy/cloudron.md).

Cloudron caveats:

- On the app, always use `php8.3` and `gosu www-data php8.3 /app/data/workdash/artisan ...`; plain `php` is the image default and `su` drops the Cloudron environment.
- The LAMP `start.sh` **sources** `/app/data/run.sh` under `set -eu`. Keep all code inside its `( ... )` subshell, or the app crash-loops before Apache starts (recovery: `cloudron debug`, see the guide's Troubleshooting).
- From PowerShell, quote the separator: `cloudron exec --app <id> '--' ls /app/data`. From Git Bash, prefix `cloudron` calls that take remote paths with `MSYS_NO_PATHCONV=1`.
- Rolling back code does not roll back migrations.
- Other agent sessions may be working in parallel (`git worktree list`, `tea pulls ls`). Check before deploying, and do not deploy a tag that would undo a fix still waiting to merge.

## Decisions and next steps

Whenever a choice is needed (or at the end of a task), give the **best next options** and mark **one as recommended**, with a one-line reason each. In Cursor, ask with the AskQuestion tool, recommended option first and labelled "(Recommended)". Do not stop with a vague "done": end with what shipped (PR, merge commit, release, deploy evidence) and the next options.
